### Detailed description (paste into the store)

> Turn Open WebUI into your Cowork — one that works in the folders on your
> own computer that you pick (one or several). Your AI chat can then list,
> read, write, search, OCR, and convert files in those folders. The extension
> processes files locally and returns requested results to the Open WebUI
> site you allow. That site and your connected AI provider may process the
> data remotely under their own privacy terms.
>
> Why: Open WebUI's code interpreter runs in a sandbox that cannot touch
> your files. Open File Bridge gives it a locked door — you choose the
> folder(s), you choose the ONE website allowed to use the door, and the
> extension enforces both.
>
> How it works:
> 1. Pick a folder in the extension's settings (add more whenever you like).
> 2. Allow your Open WebUI address (for example http://127.0.0.1:8080 or
>    https://chat.example.com) and optionally set a bridge token.
> 3. Install the bridge skill in Open WebUI (copy-paste from the GitHub
>    repo) and turn on the code interpreter in a new chat.
> 4. Ask: "list the files in my folder", or "write the summary to notes.md".
>
> Safety model:
> - Only the folders you chose — nothing outside them is visible, and each
>   folder can be set read-only or read/write on its own.
> - Site lock — requests are checked against the Open WebUI origin you
>   configure; an optional bridge token adds another check.
> - Approve/Deny cards inside the chat page for deletes and overwrites;
>   overwrites normally retain the previous version, subject to snapshot
>   size limits and filesystem availability; deletes go to a 30-day trash.
>   Recovery copies are files inside the selected folders; uninstalling the
>   extension does not remove them.
> - Read-only mode, write-rate brake, ignore patterns, and built-in refusal
>   of credential-looking files (.env, id_rsa, *.pem, …).
> - Local-first: no built-in cloud storage, extension account, analytics, or
>   telemetry. Requested file data is returned only to your configured Open
>   WebUI site. Its hosting and connected AI services have their own data policies.
>
> Extras: OCR in 20+ languages (runs locally in the extension), PDF text
> extraction, xlsx→csv and docx→html conversion, and full-text search.
>
> Where your Open WebUI must run: anywhere you can install the bridge
> skill — on the same computer (localhost), on an HTTPS LAN deployment, or
> on an HTTPS server you control. The current extension does not inject into
> ordinary plain-HTTP LAN addresses. For a public HTTPS deployment, also set
> a bridge token. Hosted Open WebUI services that don't let you install skills
> aren't supported.
>
> Requires Open WebUI with the code interpreter enabled. The bridge skill
> file, setup guide, and source code:
> https://github.com/Sparkling-AI/open-file-bridge

## 4. Privacy tab

- **Privacy policy URL** (public HTTPS):
  `https://github.com/Sparkling-AI/open-file-bridge/blob/master/docs/PRIVACY.md`
  — `docs/PRIVACY.md` covers the extension (and the desktop app); keep the
  "Last updated" date current when behavior changes.
- **Single purpose:**
  > Lets the user's own Open WebUI instance read and write files in the
  > folders on the user's computer that the user has selected (one or
  > several), under a user-configured site lock.
- **Permission — `offscreen`:**
  > Normally runs OCR (Tesseract WASM) and document conversion in an offscreen
  > document so no extra tabs or windows open on the user's machine. If the
  > offscreen document is unavailable or fails, the extension uses its bundled
  > extension-page fallback.
- **Permission — `scripting`:**
  > Used for one thing: after the user presses **Set site** or **Use this site** for their own
  > Open WebUI origin, the extension registers a single MAIN-world content
  > script (`inject-main.js`) on exactly that origin, so the chat's Python
  > sandbox can call the bridge through a page-local function instead of
  > pasting a client bootstrap into every cell. Registration is created at
  > request time for that one origin, never as a static manifest match, and
  > is unregistered when the user removes the site, revokes host access, or
  > uninstalls. No other site is scripted, and the script adds no network
  > access of its own — it only forwards messages the page's sandbox already
  > sends to the extension's service worker, which applies the same origin
  > allowlist and optional bridge token to every request.
- **Host permission justification** (the dashboard field triggered by the
  content-script matches on `https://*/*`, `http://127.0.0.1/*`,
  `http://localhost/*` — the manifest declares no separate
  `host_permissions` key):
  > Users choose their Open WebUI origin, so relay.js and confirm.js are
  > statically matched to HTTPS sites and localhost. They relay explicitly
  > shaped requests and show approval cards, without scraping page content or
  > recording browsing history. The service worker accepts file requests only
  > from the saved origin, with an optional bridge token, and confines access
  > to user-selected folders. inject-main.js is registered dynamically for
  > that origin after permission is granted. In worker mode, the relay may
  > read the page's Open WebUI sign-in token and return it over a same-origin
  > channel; the extension never sends that token to its service worker or
  > Sparkling AI.
- **Data Usage disclosures:** keep the current published disclosure:
  **Authentication information** and **Website content** only. The current
  product provides a generic file bridge and same-origin authentication
  handling, not dedicated health, payment or financial-data collection.
  Do not add categories solely by guessing what an arbitrary file could
  contain. Reassess the actual collection behavior if functionality changes.
  Local processing still needs disclosure; the privacy policy explains
  user-selected file contents and the connected Open WebUI/AI service flow.
  - **Authentication information** — the Open WebUI sign-in token (read from
    the page's local storage in worker mode, returned same-origin, never sent
    to the service worker) and the user-set bridge token (stored in IndexedDB
    and checked per request).
  - **Website content** — the text, images and other file content returned
    through the bridge at the user's request.
  - Leave **PII**, **Health**, **Financial and payment information**,
    **Personal communications**, **Location**, **Web history**, and
    **User activity** unchecked for the present submission, matching the
    existing published item and the user's clarification. Do not infer
    tracking merely from the broad content-script match.
  - Certify the limited-use statements only after confirming that the current
    implementation still uses disclosed data solely to provide the file bridge,
    does not sell or use it for advertising, and does not transfer it to
    developer-selected third parties. The user's own allowlisted Open WebUI is
    the intended recipient; the user-specified-server carve-out does not remove
    the need for accurate disclosure.

The supplied stock Open WebUI test instance has a reviewer-visible
**Local File Access** model with Code Interpreter and the extension bridge
skill already attached. Reviewers can therefore exercise the extension through
a normal chat. They do not need Workspace access, provider configuration, a
skill installation, DevTools, or the removed custom iframe permission patch.

- **Reviewer email:** `<CHROME_WEBSTORE_REVIEWER_EMAIL>`
- **Reviewer password:** `<CHROME_WEBSTORE_REVIEWER_PASSWORD>`
- **Image:** `ghcr.io/open-webui/open-webui:v0.11.3` (official stock image)

```text
Open the extension, choose a temporary folder, and set Allowed site to <CHROME_WEBSTORE_REVIEW_URL>; leave Bridge token empty. Open the supplied Open WebUI URL and sign in with the separately provided credentials. Start a new chat using Local File Access. Ask “List my files,” then ask it to create chrome-web-store-review.txt. Confirm the file appears in the selected folder, then ask the chat to read it back.
```

### Internal verification checklist

1. Extract the ZIP, load the extracted directory with **Load unpacked**, and
   open the extension's options page. (Alternatively, install the private or
   unlisted Store draft in a clean Chrome profile.)
2. Click **Choose folder…** and select an empty temporary folder. This is the
   only folder the chat will be able to see or change.
3. In **🔒 Security**, set the allowed site to exactly
   `<CHROME_WEBSTORE_REVIEW_URL>`. Leave **Bridge token** empty. The scheme,
   host, and port must match exactly.
4. Open `<CHROME_WEBSTORE_REVIEW_URL>` in Chrome and sign in with
   `<CHROME_WEBSTORE_REVIEWER_EMAIL>` and `<CHROME_WEBSTORE_REVIEWER_PASSWORD>`.
5. Start a new chat and select **Local File Access**. It is already configured
   with Code Interpreter and the bridge skill.
6. Ask: **List the files in my selected folder and tell me the folder name.**
   An empty list is valid when the temporary folder is empty. If the assistant
   reports that folder permission is needed, open the extension's options,
   click **Reconnect**, choose **Allow on every visit** in Chrome's prompt,
   return to the chat, and retry once.
7. Ask: **Create a text file named `chrome-web-store-review.txt` containing
   exactly: `Open File Bridge Chrome Web Store review succeeded.`** Creating a
   new file does not require destructive-action approval.
8. Confirm that `chrome-web-store-review.txt` appears in the selected folder
   on the review computer and contains the requested sentence.
9. Ask: **Read `chrome-web-store-review.txt` and repeat its exact contents.**
   The response should reproduce the sentence from the local file.
10. Delete the temporary file and folder after the test.

Pass condition: the chat lists the selected local folder, creates the requested
file in that folder, and reads the same file back. File access is performed by
the installed extension on the reviewer's computer; the Cloud Run service
provides only the stock chat UI and model access.

### Optional deterministic relay check

If chat/model access is temporarily unavailable, the reviewer can still test
the extension transport directly from the allowed page's DevTools console.
Paste the helper below, then run `await ofb("GET", "/list")`; expect `ok: true`
and `status: 200`.

```js
async function ofb(method, path, body) {
  return new Promise((resolve, reject) => {
    const id = "cws-" + crypto.randomUUID();
    const timer = setTimeout(() => {
      removeEventListener("message", onMessage);
      reject(new Error("timed out — is the extension injected on this page?"));
    }, 5000);
    function onMessage(ev) {
      const m = ev.data;
      if (!m || m.ofb !== true || m.id !== id ||
          typeof m.ok !== "boolean" || typeof m.status !== "number") return;
      clearTimeout(timer);
      removeEventListener("message", onMessage);
      resolve(m);
    }
    addEventListener("message", onMessage);
    postMessage({ ofb: true, id, method, path, body }, "*");
  });
}
```

To verify the site lock, open `https://example.org`, paste the helper again,
and run `await ofb("GET", "/list")`. Expect `ok: false`, `status: 403`, and an
`origin_blocked` response because that origin was not allowed.
