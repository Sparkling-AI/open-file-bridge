1. How your files are protected

Every change the AI makes goes through the same three safety nets — no change is ever unrecoverable:

What the AI doesWhat the bridge does firstHow you undo it
Overwrite / edit a fileCopies the current version to the version history (a “snapshot”)Restore an older version below
Delete a file or folderMoves it to the trash — nothing is erasedFind a deleted file below
Restore an old versionSnapshots the current version first (so restoring is itself undoable)Same as a restore — just pick a newer timestamp
Mass-edit many filesEach file is snapshotted individually + the write-rate brake caps the paceRestore each file, or use your own backup for bulk reverts

The one-liner to remember: in chat, just say —

“Show me the previous versions of <file> and restore the one from before the AI's edit.”

2. Restore an older version of a file

Every overwrite keeps the previous content. Two ways to get it back:

Option A — in chat (easiest)

Ask your assistant directly:

List the saved versions of reports/summary.docx.

It will call /versions/list and show you something like:

20260906-143205-a1b2   reports/summary.docx   14 KB   (2 hours ago)
20260906-091511-c3d4   reports/summary.docx   11 KB   (today, morning)

Pick the one you want and say:

Restore 20260906-091511-c3d4 of reports/summary.docx

That's it. The bridge restores it and — importantly — snapshots the current content first, so even the restore can be undone the same way.

Option B — with curl (no chat needed)

# 1) list snapshots (metadata only)
curl -s -X POST http://127.0.0.1:8765/versions/list \
  -H "Content-Type: application/json" \
  -H "X-Bridge-Token: <your token, if set>" \
  -d '{"path":"reports/summary.docx"}'

# 2) restore the one you want (ts = timestamp from the list above)
curl -s -X POST http://127.0.0.1:8765/versions/restore \
  -H "Content-Type: application/json" \
  -H "X-Bridge-Token: <your token, if set>" \
  -d '{"path":"reports/summary.docx","ts":"20260906-091511-c3d4"}'

Paths are relative to your shared folder. Your bridge port is 8765 unless you changed it.

3. Find a deleted file (trash)

“Delete” in Open File Bridge never erases — it moves the file to a trash store that lives outside your shared folder. Entries are kept for 30 days, then cleaned up automatically.

Option A — in chat

What's in the trash? I'm looking for a file I deleted yesterday.

then

Restore the trash entry 20260905-180033-77aa of notes/old-draft.md

Option B — with curl

# 1) list trash entries
curl -s -X POST http://127.0.0.1:8765/trash/list \
  -H "Content-Type: application/json" -H "X-Bridge-Token: …" -d '{}'

# 2) restore one (path + ts both come from the list)
curl -s -X POST http://127.0.0.1:8765/trash/restore \
  -H "Content-Type: application/json" -H "X-Bridge-Token: …" \
  -d '{"path":"notes/old-draft.md","ts":"20260905-180033-77aa"}'

Two small rules:

• Trash-restore refuses if a file with that name already exists again (“delete or rename it first”) — it will never itself overwrite something.

• The trash is for AI/chat deletions. If you delete a file in Finder / Explorer, that's outside the bridge — use your OS trash as usual.

4. “The AI messed up my file!” — full walkthrough

The AI rewrote reports/summary.docx and you want yesterday's content back:

  1. Don't panic-edit the file — the old content is already safe in the version history (the bridge snapshotted it before the AI's write landed).
  2. In chat: “Show me the saved versions of reports/summary.docx.”
  3. Compare sizes/timestamps and pick the snapshot from before the edit.
  4. “Restore that one.” The current (messed-up) content is snapshotted on the way in — so if you change your mind, the AI's version is also recoverable.
  5. Optional: “Open the folder so I can check.” — the 📂 Show in folder link in chat opens it with the file selected.

5. “I regret the whole edit” — many files

When a task touched many files (a rename sweep, a mail-merge, a batch rewrite), each file still has its own snapshot. In chat:

The last task rewrote several files. For each of:
  contracts/acme.md, contracts/beta.md, reports/q3.docx
list the versions and restore each one to the version from before today's task.

The bridge snapshots every overwrite individually, so “batch regret” is just N single-file restores. For very large batches (or when in doubt), your own folder backup is still the gold standard — the version history is a safety net, not a backup product.

6. The write-rate brake (why writes suddenly stop)

If the AI starts writing unusually fast (typically a stuck loop), the bridge refuses further writes for up to a minute instead of hammering your folder. You'll see an error in chat like:

write-rate circuit breaker: 21 writes / 130 KiB in the last 60 s (limits 20 / 50 MiB). STOP and ask the user to confirm the mass edit before continuing.

What to do: nothing is broken and nothing was half-written. Either…

  • reply in chat to confirm you want the mass edit and let it continue (it resumes automatically as the 60-second window slides), or
  • tell the AI to stop, and review what was written so far (each write is snapshotted anyway), or
  • raise the limits for this session in the app's settings page → Safety section.

7. Safety settings (settings page)

Open the Open File Bridge app (or http://127.0.0.1:8765) → 🛟 Safety card:

  • Write limit per minute — how many writes the AI may do per rolling 60 s before the brake engages (default 20).
  • Write volume per minute — the same brake, measured in MB (default 50).
  • Read-only mode — a master switch that blocks every write (including yours-via-chat). Handy when you want the AI to analyze but never modify.

Values set by environment variables (FILE_BRIDGE_MAX_WRITES, FILE_BRIDGE_MAX_WRITE_MB, FILE_BRIDGE_READONLY) are fixed for the session and cannot be overridden from the page — the page will say so instead of pretending.

8. Where snapshots & trash live, and their limits

  • Location — outside every shared folder, in the bridge's own state folder: ~/.local/state/open-file-bridge/ (Linux), ~/Library/Application Support/open-file-bridge/ (macOS), %APPDATA%\open-file-bridge\ (Windows). The file API can never read old versions back into the chat — that's deliberate.
  • Per-file cap — files over 8 MB are not snapshotted (the write still happens; the response says skipped: too_large).
  • Total cap — the version store keeps the most recent ~512 MB of snapshots; the oldest are pruned first. Trash entries expire after 30 days.

9. FAQ

The AI overwrote a 20 MB file — where's my snapshot?

Above the 8 MB per-file cap, the write succeeds but is not snapshotted. That's the documented behavior of the safety net; keep large files out of the shared folder or rely on your own backup for them.

Can the AI restore versions by itself?

Only when you ask. Restores are normal bridge calls, so the model can list versions and restore one as part of your conversation — the skill tells it to confirm which file+timestamp you mean before overwriting anything.

Is the version history a backup?

No. It lives on the same disk, is capped (512 MB store, 8 MB/file), and prunes oldest-first. It's an undo net for AI edits — pair it with a real backup for irreplaceable data.

I stopped the bridge — are my snapshots gone?

No. Snapshots and trash live on disk in the state folder and survive restarts and app updates.

Someone else's chat connected to my bridge — can they restore my files?

Restores use the same bridge endpoints as any write, so the same security applies: origin lock and (recommended) bridge token. See the admin guide.
